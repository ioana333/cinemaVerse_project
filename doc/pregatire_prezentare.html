CinemaVerse – ghid de rulare și pregătire

Predare etapa 1 – 1 decembrie · bifează pașii pe măsură ce îi faci

A. Rularea proiectului, pas cu pas

Atenție: 01 șterge și recreează baza CinemaVerse. Dacă o rulezi după ce ai introdus date proprii, le pierzi. Dacă SSMS spune că baza e folosită, închide celelalte ferestre de query către ea (scriptul face deja SINGLE_USER, dar fereastra ta trebuie să fie pe master).

Dacă ceva dă eroare, citește numărul liniei din mesaj; cel mai des cauza e rularea scripturilor în altă ordine.

Diagrama din SSMS (pentru capturi)

  1. Object Explorer → CinemaVerse → Database Diagrams → click dreapta → New Database Diagram (acceptă „Yes” dacă cere să instaleze suportul pentru diagrame).
  2. Selectează toate cele 10 tabele → Add → Close. Aranjează-le (click dreapta → Arrange Selection) și fă captură de ecran.
  3. Salvează diagrama ca CinemaVerse_diagram. Poți pune captura în documentație lângă diagrama SVG deja existentă.

Opțional: conectare cu utilizatorii creați

Ca să te conectezi efectiv ca cv_cashier, serverul trebuie să accepte „SQL Server and Windows Authentication mode” (click dreapta pe server → Properties → Security → apoi restart serviciu). Nu e obligatoriu: testele EXECUTE AS din 04_security.sql arată același lucru. Parolele sunt în script (ex.: Cashier#2026!cv).

Documentația

Deschide documentatie.html cu dublu click (în Chrome/Edge). Pentru PDF: Ctrl+P → „Save as PDF”.

B. Ce să ai pregătit înainte de prezentare

C. Planul prezentării (aprox. 10 minute)

Cerința pentru 1 decembrie: specificații, structura bazei de date, constrângeri, vederi, tipuri de utilizatori și roluri, drepturi. Exact în ordinea asta:

1. Specificații și cazuri de utilizare (1–2 min)

Arată secțiunile 1–2 din documentație. Spune: „Platformă de cinema inspirată de Cinema City: catalog de filme, program pe săli, vânzare de bilete pe loc, conturi de clienți, recenzii, angajați. Cinci tipuri de utilizatori: client, casier, manager, analist, administrator.”

2. Structura bazei de date (3 min)

Arată diagrama. Punctează:

  • 10 tabele. Relații 1-n: Cinemas→Halls, Halls→Screenings, Screenings→Tickets etc.
  • m-n: Movies↔Genres (prin MovieGenres) și Customers↔Movies (prin Reviews, care are atribute proprii: notă, comentariu).
  • Recursivă: Employees.manager_id → director → manager → casier.

Demo în SSMS (rulează separat):

SELECT * FROM Halls;                 -- capacity e coloana calculata
SELECT * FROM MovieGenres;           -- tabela asociativa m-n
SELECT * FROM vw_EmployeeHierarchy ORDER BY path;   -- ierarhia recursiva

3. Constrângeri și indecși (2 min)

Arată 2–3 constrângeri care chiar se declanșează. Execută fiecare și arată eroarea:

USE CinemaVerse;
-- loc vandut de doua ori (UNIQUE pe screening_id, seat_row, seat_number)
INSERT INTO Tickets (screening_id, customer_id, seat_row, seat_number, price_paid)
VALUES (1, 2, 5, 10, 45);

-- rating invalid (CHECK 1..10)
INSERT INTO Reviews (customer_id, movie_id, rating) VALUES (8, 1, 11);

-- angajat propriul manager (CHECK)
UPDATE Employees SET manager_id = employee_id WHERE employee_id = 3;

-- stergere film cu proiectii (FK fara CASCADE)
DELETE FROM Movies WHERE movie_id = 1;

-- CASCADE vs SET NULL: stergi un client, biletele raman cu customer_id NULL
BEGIN TRAN;
DELETE FROM Customers WHERE customer_id = 1;
SELECT ticket_id, customer_id FROM Tickets WHERE ticket_id IN (1,2);
ROLLBACK;

La indecși: „PK = clustered, UNIQUE creează indecși unici, plus index non-clustered cu INCLUDE pe program, index filtrat pe bilete cu cont și index unic filtrat pe telefon (permite mai mulți NULL).”

4. Vederi (1–2 min)

SELECT * FROM vw_UpcomingScreenings ORDER BY start_time;   -- locuri libere
SELECT * FROM vw_MovieCatalog;                              -- genuri + nota medie
SELECT * FROM vw_Revenue ORDER BY revenue DESC;

Spune ce problemă rezolvă fiecare (program pentru public, raportare pentru analist, ierarhie fără salarii, profil client fără date personale).

5. Utilizatori, roluri, drepturi (2–3 min)

Arată matricea din secțiunea 7 a documentației, apoi demonstrează:

EXECUTE AS USER = 'cv_cashier';
SELECT TOP 3 title, free_seats FROM vw_UpcomingScreenings;   -- merge
SELECT salary FROM Employees;                                -- DENY
REVERT;

EXECUTE AS USER = 'cv_analyst';
SELECT * FROM vw_Revenue;                                    -- merge
DELETE FROM Tickets;                                         -- DENY
REVERT;

EXECUTE AS USER = 'cv_manager';
SELECT * FROM vw_EmployeeHierarchy;                          -- merge (fara salarii)
SELECT salary FROM Employees;                                -- DENY
REVERT;

Mesaj-cheie: „Drepturile sunt date rolurilor, nu utilizatorilor; am aplicat privilegiul minim. Salariile și datele personale se văd doar prin vederi sau coloane permise.”

D. Întrebări probabile și răspunsuri

De ce ai ales ierarhia recursivă pe Employees?Un cinema are director → manageri → casieri/operatori. Un singur tabel cu manager_id reprezintă orice adâncime; o parcurg cu CTE recursiv în vw_EmployeeHierarchy.
Cum garantezi că un loc nu se vinde de două ori?Constrângerea UNIQUE (screening_id, seat_row, seat_number) pe Tickets. Chiar dacă două persoane cumpără simultan, a doua primește eroare de cheie duplicat.
Cum verifici că locul există în sală (rând/loc ≤ dimensiunea sălii)?Un CHECK nu poate compara cu alt tabel, deci această regulă o fac cu un trigger DML la etapa următoare (e menționat în documentație).
Ce diferență e între clustered și non-clustered?Clustered ordonează fizic datele tabelei după cheie – un singur index clustered pe tabel (PK-ul meu). Non-clustered e o structură separată cu pointer către rânduri; pot fi mai multe.
Ce e un index filtrat? De ce îl folosești?Index doar pe rândurile care îndeplinesc o condiție (WHERE customer_id IS NOT NULL). E mai mic și permite unicitate doar pentru valori existente (telefon).
De ce ON DELETE SET NULL la Tickets.customer_id, dar CASCADE la Reviews?Biletele sunt date financiare/istorice (încasări) și trebuie păstrate chiar dacă clientul își șterge contul; recenziile fără autor nu au sens, deci se șterg odată cu clientul.
De ce roluri și nu drepturi direct pe utilizatori?Se administrează mai ușor: un casier nou se adaugă în role_cashier și primește automat drepturile. Se reduce riscul de erori.
De ce managerul poate vedea vw_EmployeeHierarchy dacă are DENY pe Employees?Ownership chaining: vedere și tabel au același proprietar (dbo), deci SQL Server nu mai verifică drepturile pe tabelul de bază când accesul se face prin vedere. Vederea nu include salariul, deci expune doar ce e permis.
Ce face coloana capacity din Halls?Coloană calculată persistată: seat_rows × seats_per_row. Se actualizează automat și o folosesc la calculul locurilor libere.
Ce urmează pentru prezentarea finală?Proceduri stocate CRUD, funcții T-SQL, triggere DML și DDL, cursoare, job-uri și strategia de backup/restore.

E. Dacă ceva nu merge

  • „Cannot drop database because it is currently in use”: deschide un query nou pe master, rulează ALTER DATABASE CinemaVerse SET SINGLE_USER WITH ROLLBACK IMMEDIATE; apoi rulează din nou 01.
  • „Invalid object name”: ai rulat un script în altă bază; pune USE CinemaVerse; sus sau alege baza din dropdown.
  • Proiecțiile nu apar în vw_UpcomingScreenings: vederea arată doar proiecții viitoare, iar datele de test sunt generate la ziua rulării. Reîncarcă baza rulând din nou 01 și 02.
  • Eroare la CREATE LOGIN: rulează 04_security.sql cu un cont care e sysadmin (Windows Authentication, ca administrator).
